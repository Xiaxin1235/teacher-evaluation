# 教师评估 AI 平台 —— 项目大纲

> 版本：v0.1（大纲稿，用于启动讨论）
> 定位：一个类似 "pi agent" 的多模型 Agent 平台，接入各家大模型 API，对本地教师相关数据库进行检索与分析，完成对教师教学水平等各项指标的**量化且可追溯**的评估。核心命题：**用户提问可以笼统宽泛，但系统必须通过证据链给出严谨的综合结论**。

---

## 0. 文档目的

- 对齐项目愿景、边界、分期目标，避免一上来就做"什么都有的平台"。

- 明确需要"业务方"（学校/教育局）拍板的关键决策点（见 §12）。

## 1. 项目愿景与目标

**一句话愿景**：把教师评估从"经验判断 + 手工统计"升级为"多源数据 + 指标模型 + AI 证据化解读"，让每一次评估结论都**有数据、有依据、可复核**。

**核心用户故事**：

1. 管理者提问："张老师近三年的教学水平整体怎么样？" → 系统自动拆解维度、检索多源数据、按指标加权、输出带证据引用的评估报告，并说明数据覆盖度和置信度。
2. 教研员提问："这学期初二年级数学组的教学效果相比上学期有什么变化？" → 系统做对比分析、趋势判断、异常点提示。
3. 教师本人提问："我哪方面最弱？建议如何提升？" → 系统基于本人脱敏数据给出发展性建议（此功能放后期阶段）。

**必须坚持的原则**：

- **结论可追溯**：任何一条结论都挂接证据（来源表、时间、数值）。
- **不确定要明说**：数据缺失、样本过小、指标权重争议都要显式披露，禁止用平滑的 AI 语言掩盖。
- **评估框架由业务方掌控**：维度、指标、权重是"配置"，不是模型自己发明。
- **只读优先**：MVP 阶段系统只读数据，不做任何写入/修改操作。

---

## 2. 核心挑战：为什么"宽泛提问 → 严谨回答"很难

这是本项目最重要的技术命题，必须在架构上正面解决：

| 挑战 | 表现 | 应对思路 |
|---|---|---|
| 意图歧义 | "教得怎么样"可以指课堂、成绩、评教、师德任何一个维度 | Planner 先做边界澄清（必要时反问用户），再分解子问题 |
| 数据缺口 | 某个维度根本没有数据 | 明确标注"该维度无数据支撑"，宁缺毋滥 |
| 口径不一致 | 不同班级/年份成绩可比性差 | 指标计算层统一口径、归一化、注明基线 |
| 模型幻觉 | LLM 编造不存在的"数据" | 强制引用检索出的证据块，无证据则拒绝作答 |
| 评估结论被滥用 | 单一数字被用于人事决策 | 输出维度雷达图而非单一总分；附置信度与免责声明 |
| 权重主观性 | "教学效果占 40% 还是 60%？" | 权重由业务方配置并版本化，系统不默认裁决 |

**结论机制设计（评估流水线）**：

```
宽泛问题
  → 意图理解 + 边界澄清（必要时反问）
  → 拆解为 N 个子问题
  → 每个子问题：检索证据 → 匹配指标 → 计算得分(带置信度)
  → 综合加权 → 一致性校验(critic) → 输出报告
  → 报告附：证据引用列表 / 数据覆盖率 / 置信区间 / 缺口清单
```

## 3. 系统定位与范围

**In scope**：

- 教师多源数据的接入、清洗、检索、统计。
- 可配置的评估指标体系（维度/指标/权重/数据源映射）。
- 文档问答与评估报告生成（对话式 + 批量化）。
- 多模型 API 接入、任务路由、降级容错。
- 权限、审计、脱敏、评估结果的水印与留痕。

**Out scope（一期明确不做）**：

- 真实课堂音视频自动分析（后期可作为独立子系统）。
- 替代学校人事考核流程本身（只做辅助分析，不做裁决）。
- 对教师隐私数据的外部网络传输（见合规 §7）。

**分期思路**：先"能算"（指标计算管线），再"会答"（Agent 引擎），最后"好看好用"（看板与工作流）。

## 5. 六大子系统设计（概要）

### 5.1 数据接入与治理层

- **数据来源盘点（典型）**：教务系统（课程、班级、课时）、人事系统（职级、年龄、教龄）、学生成绩库（成绩分布、及格率、进步度）、学生评教问卷、教研活动记录、获奖与论文记录、历年年终考核表。
- **形态**：可能是关系库、Excel/CSV 导出、OA 系统，全部归一到**标准教师主数据模型**（schema versioned）。
- **ETL 管线**：定时增量同步 + 数据质量校验（空值率、异常值、断档年份）→ 质量报告。
- **脱敏层**：姓名/工号可标识字段与业务字段分离存储；分析库中做去标识化（pseudonymization）。

### 5.2 评估指标体系层（评估框架即配置）

- 用结构化配置（YAML/JSON，入库管理）定义：`维度 → 指标 → 权重 → 数据源字段 → 统计口径 → 达标线 → 置信度规则`。
- 示例骨架（**权重与口径须由业务方确认**）：

| 维度 | 示例指标 | 数据源 | 口径说明 |
|---|---|---|---|
| 教学设计 | 教案完整度/更新频率 | 教案库 | 学期内教案与课表匹配率 |
| 课堂教学 | 听课评分、课堂出勤率 | 听课记录/教务 | 由教研组多人打分取均值 |
| 教学效果 | 成绩分布、及格率、进步度 | 成绩库 | 需控制班级起点差异（增值视角） |
| 教研与学术 | 公开课、论文、课题 | 科研系统 | 按级别赋分 |
| 学生发展 | 学生评教、竞赛获奖 | 评教系统 | 注意评教的主观性加权 |
| 师德师风（红线） | 投诉记录、违规记录 | 人事 | 红线类：一票否决，不参与加权 |

- **版本化**：每学期/每学年评估框架作为一个"评估模板版本"，保证历史可比。
- 附带**口径字典**：统一"及格率怎么算""评教平均分是否去掉高低分"等规则，避免模型自由发挥。

### 5.3 检索与证据层

- **RAG 双轨**：
  - 结构化查询轨：指标计算直接走 SQL/聚合，得到确定数值；这是**主证据**。
  - 向量检索轨：教案、评语、教研记录等非结构化文本，切块入库（pgvector/Milvus），用于定性佐证。
- **证据块协议**：每个证据 = `{来源表/文档, 时间范围, 原文摘录, 数据口径, 可信度}`，是 LLM 唯一允许引用的素材。
- **指标仓库**：预计算常用指标（按教师×学期×维度），避免每次问答全量重算；支持 OLAP 式对比与趋势查询。

### 5.4 分析引擎层（多智能体编排）

- 采用 **Planner / Worker / Critic** 模式（可用 LangGraph 或自研状态机实现）：
  - **Planner**：理解宽泛问题 → 识别评估对象、时间范围、意图 → 可选反问澄清 → 产出子任务 DAG（并行/串行）。
  - **Retriever（工具）**：调结构化查询 + 向量检索，只返回证据块。
  - **Analyzer（各维度 Worker）**：每维独立计算得分与置信度，输出半结构化中间结果。
  - **Synthesizer**：按配置权重综合，生成报告叙事，每条结论内联证据引用。
  - **Critic**：LLM-as-judge 校验——有无幻觉/矛盾/过度解读/证据不足，不通过则打回重写一轮。
- **记忆与上下文**：会话级记忆 + 项目级缓存（同问同答要稳定，避免方差）。
- **反问机制**：问题严重不明确（对象、时间段都缺失）时，第一轮先反问而不是硬答。

### 5.5 多模型接入与路由层（"pi agent" 式能力）

- **统一模型网关**：一个 OpenAI 兼容适配层，屏蔽各家 API 差异（LiteLLM 或自研 adapter）。
- **任务路由**：按任务类型（简单问答 / 深度推理 / 批量计算 / 结构化抽取）＋ 成本上限 ＋ 可用性，选择模型；支持多供应商配置与密钥管理。
- **高利害题双模型交叉校验**：评估结论类问题默认让两个模型独立作答，不一致时由 Critic 裁决或要求重答。
- **降级容错**：主模型超时/限流 → 自动切换备份模型并记录。
- **模型卫生**：输入输出过滤、越权问题拦截、提示词注入防护。

### 5.6 应用与交互层

- **对话式评估台**（主力交互）：支持追问、下钻（"原因呢？""只看 2024 年？"）、导出报告（PDF/Word）。
- **批量评估任务台**：上传名单/条件 → 排队批量生成评估报告 → 人工抽检。
- **管理控制台**：指标体系配置、数据源状态、模型路由配置、评估记录审计。
- **面向角色的视图**：管理者（全校视角、对比、风险提示）、教研员（学科视角）、教师本人（个人报告，仅本人数据）。

## 6. 技术栈建议（待定案）

| 层 | 建议 | 备注 |
|---|---|---|
| 后端 | Python 3.11+ / FastAPI（数据科学生态强） | 或 TypeScript/NestJS，取决于团队 |
| 主数据库 | PostgreSQL + pgvector | 结构化数据 + 向量同库，省运维 |
| 统计/指标 | Pandas / DuckDB（快速列式计算） | 指标仓库预计算 |
| 编排 | LangGraph（或自研状态机） | MVP 可先用单 agent + 工具链 |
| 模型网关 | LiteLLM / 自研 adapter | 必须有统一抽象 |
| 前端 | React + Ant Design / Vue3 + Element Plus + ECharts | 看板与报告可视化 |
| 部署 | Docker Compose（单机）→ K8s（多校） | 默认私有化部署 |
| 任务队列 | Celery / SQLite 简单队列 → Redis | 批量评估用 |

**选型原则**：优先自托管、易私有化、零件少；不要把系统绑死在单一云厂商。

## 7. 安全、隐私与合规

- 教师个人信息属**敏感个人信息**，须遵循《个人信息保护法》；涉及教育数据还须注意地方政府数据条例。
- **最小化采集**：只接评估所需字段；不采集与评估无关的隐私字段。
- **去标识化**：分析库使用 pseudonym，评估报告对教师本人外角色做字段级脱敏。
- **部署形态决定合规路径**：强烈建议**私有化部署**（教师数据不出校/局），模型调用走 APA/专线或由学校配发的私密网关，**不得将原始教师数据发送第三方模型**（可用脱敏摘要或本地小模型兜底）。
- **权限矩阵**：角色 × 数据范围 × 操作（读/导出）三级控制；全量导出需二次审批。
- **审计日志**：谁、何时、对哪个教师、基于哪个评估模板、调用了哪些模型，全留痕。
- **结果留痕**：每条评估报告存版本快照，追溯"当时为什么得出这个结论"。

## 8. 质量保障与评测

- **Golden Set**：业务专家准备 50~200 条标准问答（覆盖各维度、含边界/刁钻问题），作为回归基准。
- **评测矩阵**：事实准确性（证据引用是否为真）、完整性（缺口是否披露）、一致性（同题同答的稳定性）、合规性（是否越权/涉敏）。
- **自动评测**：用 LLM-as-judge + 人工抽检双轨；每次指标体系或模型改动后全量回归。
- **对抗测试**：诱导性提问（"帮我直接给张老师打 95 分"）、越权提问（"查所有老师的排名"）、幻觉测试（问不存在的数据）。
- **业务验收**：由教务/人事负责人对 20 份样例报告人工复核，通过率 ≥ 90% 才放量。

## 11. 风险清单

| 风险 | 等级 | 缓解 |
|---|---|---|
| 数据质量差/字段缺失 → 回答不可靠 | 高 | 数据盘点前置、覆盖率显式披露、宁可拒绝回答 |
| 指标口径争议（业务方内部不一致） | 高 | 权重与口径必须业务方签字，版本化留档 |
| 模型幻觉污染评估结论 | 高 | 证据引用强制、无证据拒绝作答、Critic 校验、双模型交叉 |
| 评估结果被误用于人事处罚引发纠纷 | 高 | 输出置信度与局限说明、权限最小化、审计留痕、法律评审 |
| 教师隐私泄露 | 高 | 私有化部署、去标识化、字段最小化、不向外部模型传原始数据 |
| 多校复用模板差异大 | 中 | 评估模板按校配置，平台做模板市场而非强统一 |
| 宽泛问题被误解导致答非所问 | 中 | 反问机制、对话下钻、边界澄清 |
| 项目范围失控（一开始就想做全部） | 中 | 严守 §3 分期 Out-of-scope |

## 12. 待决策事项（需要业务方拍板）

1. **部署形态**：学校/教育局私有化，还是 SaaS？（强烈建议私有化，见 §7）
2. **数据来源清单**：现在有哪些系统/表格？谁提供样例数据？更新频率？
3. **评估用途**：发展性（帮老师成长）还是考核性（参与评优/晋升）？——**这决定整套设计基调**。
   - ✅ **已确认：考核性**。随之定下四条设计基线（已写入设计文档 §新增）：
     ① 评分校准（相对/百分位排名，防全体偏高、防均值失真）；
     ② 人工复核清单（关键维度强制人工确认）；
     ③ 申诉与复核闭环（教师可对评估提出异议，出具口径与证据复核说明）；
     ④ 合规底线（AI 输出为辅助材料，最终评定由评审委员会人工确认——自动化决策需遵循《个保法》第24条）。
   - ⏳ **待定**：评优/晋升的具体规则与名额（业务方后续补充）。
4. **指标体系主导权**：谁来定义维度与权重？（建议成立"教务处 + 教研组长 + 人事"三方小组）
5. **模型来源**：优先接入哪些模型？（国内合规候选：DeepSeek、通义、文心、Kimi 等；是否允许接入海外 API）
6. **用户角色**：管理员 / 教研员 / 教师本人之外，是否还有教育局账号？
7. **报告出口**：是否需要对接 OA/教育局填报格式？
