> 前置文档：《教师评估AI平台-项目大纲.md》《需求确认单.md》
> 状态：草案。待业务方在需求确认单签字后定稿基线。
> 约定：本设计以"只读评估"为前提（MVP 不写业务库）；所有评估框架为可配置数据，不硬编码在代码里。
> **评估用途：考核性**（评优/晋升参考；AI 输出仅作辅助材料，最终评定由评审委员会人工确认）。

## 0. 考核性评估的设计基线（本章为考核性场景新增，优先级最高）

> 考核性 ≠ 发展性。考核性场景下，一个分数可能影响评优、晋升甚至续聘，因此情绪风险与合规风险更高，设计必须额外满足四条刚性要求：

### R1 评分校准

- **禁止"越严厉越吃亏/越宽松越占便宜"的部门间扭曲**：不同教研组的原始分不可直接横向比较。
- 指标得分提交前须做**距离校准**：按"同校 × 同学科 × 同周期"分桶，输出 **原始分 + 百分位排名 + 组内 z-score** 三件套，杜绝"全校直接用原始分排名"造成的不公平。
- 若某学科/部门样本 < 5 人，做跨学科合并校准并显著标注"样本过小，校准幅度受限"。

### R2 人工复核清单

- 引擎每出一份结果，同时生成 **Human-in-the-loop 复核清单**：列出过程性维度（如课堂教学、教学设计）等需要教研组长人工确认的项目，并标注"原始证据值 / 计算分 / 置信度 / 需人工打勾"。
- 实现状态：M05 已交付 `data/ddl/05_review_appeal.sql`（`human_review_checklist` 表）。

### R3 申诉与复核闭环

- 教师对单项或总分有异议，可提交 **申诉（appeal）**：系统只做"哪些数据参与、口径是什么、为何这一步取这个值"的**追溯说明**，不自行改分；最终由评审委员会人工终裁。
- 需要保留 `appeal_record` 表：申诉时间、理由、追溯说明、委员会结论、改分记录（如有）。
- 实现状态：M05 已交付 `data/ddl/05_review_appeal.sql`（`appeal_record` 表 + `trace_json` 结构定义）。

### R4 合规与决策权归属

- **AI 系统不产生具有法律/人事效力的最终结论**：评估报告标题固定标注"辅助参考材料，供评审委员会人工复核使用"。
- 对标《个人信息保护法》第 24 条：自动化决策不得对个人权益产生重大影响，除非获得同意或经人工介入——本项目定位为**预筛/辅助+人工裁决**，避开"全自动考核"。
- 红线项（师德投诉、违规）一旦查实，进入**独立人事流程**，不在评分体系内做算术处理。

## 1. 设计目标与原则回顾

- **结论可追溯**：每个结论 → 证据块 → 来源表/文档 + 时间范围 + 口径。
- **宽泛提问 → 严谨回答**：Planner 分解 + 反问责制 + Critic 校验。
- **评估框架即配置**：维度/指标/权重/口径全部可配、版本化。
- **不确定要明说**：覆盖率、置信度、缺口显式披露。

## 3. 评估指标体系（配置文件样例）

以 YAML 说明"评估框架即配置"如何落地。以下为**示例**，权重/口径须业务方确认。

```yaml
# evaluation_templates/2025-2026_v1.yaml
template:
  name: "2025-2026学年 教学评估 v1"
  school_year: "2025-2026"
  version: 1
  weight_total: 1.0

dimensions:
  - key: teaching_design
    name: 教学设计
    weight: 0.20
    metrics:
      - key: lesson_plan_coverage      # 教案覆盖度 = 已交教案课时 / 应授课时
        weight: 1.0
        source:
          type: table_query
          table: lesson_plan
          aggregation: "COUNT(DISTINCT plan_date) / class_hours(school_year, semester, teacher_id)"
        scoring:
          base: 60            # 60 分起评
          full_mark_at: 1.0   # 覆盖率 100% 得满分
        benchmark: { pass: 0.80, excellent: 0.95 }

  - key: classroom
    name: 课堂教学
    weight: 0.25
    metrics:
      - key: observation_score
        weight: 0.70
        source:
          type: table_query
          table: class_observation
          aggregation: "AVG(score) BY teacher_id, semester -- 教研组多人打分取均值"
        confidence:
          min_samples: 3     # 听课次数 < 3 则置信度下调
      - key: attendance_rate
        weight: 0.30
        source:
          type: table_query
          table: course_period
          aggregation: "AVG(attendance_rate) BY teacher_id, semester"

  - key: teaching_effect
    name: 教学效果
    weight: 0.35          # 效果类权重最高，但必须以增值/控制基线方式计算
    metrics:
      - key: pass_rate_improvement   # 增值视角：本班及格率 - 同课均值 的学期间变化
        weight: 0.50
        source:
          type: table_query
          table: exam_score
          aggregation: "delta(pass_rate(class_id, course_id, school_year, semester)) vs baseline"
        note: "必须控制班级起点差异，用同年级同科目基线，禁止直接跨班比绝对值"
      - key: score_distribution_index
        weight: 0.30
        source:
          type: table_query
          aggregation: "z-score of mean, std by class vs same-course cohort"
      - key: progress_rate
        weight: 0.20
        source:
          type: table_query
          aggregation: "pct of students with rank improvement ≥ 10% within cohort"

  - key: research_activity
    name: 教研与学术
    weight: 0.10
    metrics:
      - key: open_class_count      # 公开课次数（按级别加权）
      - key: papers_and_projects   # 论文 / 课题（按级别赋分，见 score_dict）
        source:
          type: table_query
          table: research_record
          score_dict: { national: 100, provincial: 80, municipal: 60, school: 40 }

  - key: student_feedback
    name: 学生评教
    weight: 0.10
    metrics:
      - key: survey_avg
        weight: 0.60
        source:
          type: table_query
          table: student_survey
          aggregation: "AVG(score) -- 建议去掉最高最低各 5%"
        confidence: { min_responses: 20 }   # 样本过小置信度降低
      - key: survey_participation_rate
        weight: 0.40

  - key: ethics_redline
    name: 师德师风（红线）
    weight: 0          # 不参与加权
    is_redline: true
    metrics:
      - key: verified_complaint
        source: { type: table_query, table: complaint_record }
      - key: discipline_violation
        source: { type: table_query, table: discipline_record }
    rule: "存在任一查实记录 → 总评标记 redline_flagged=Y，报告显著提示，不参与综合评分"
```

**口径字典（口径库，防 LLM 自由发挥）**

```yaml
glossary:
  pass_rate: "及格率 = 成绩 ≥ 60 的学生数 / 参考学生数；剔除缺考与免考标记"
  class_baseline: "同校同年级同科目全体班级为基线；班级规模 < 10 人时标注低样本"
  survey_avg: "同学期同教师评教问卷均值；剔除最高最低各 5% 后计算"
  improved_student: "本学期位次较上学期提升 ≥ 全年级 10% 百分位的学生"
```

## 4. 评估引擎设计

### 4.1 两种执行模式

| 模式 | 触发 | 说明 |
|---|---|---|
| **批量评估** | 周期任务/管理台 | 全量教师 × 模板跑指标管线，结果落库（主档+维度得分+证据） |
| **对话式评估** | 用户提问 | 实时按需计算所需维度；使用指标仓库缓存，未命中才重算 |

### 4.2 对话式评估时序（宽泛问题示例："张老师近三年教学水平怎么样？"）

```
User ──▶ Gateway ──▶ Planner
 1. Planner 解析：对象=张老师(teacher_id 解析)，范围=近三年(2022-2025 三个学年)，
    意图=综合评估。缺失项（如"只看效果还是全维度"）→ 可反问或按默认覆盖全维度 + 注明。
 2. 分解子任务 DAG：
    T1 教学效果 ｜ T2 教学设计 ｜ T3 课堂教学 ｜ T4 教研学术 ｜ T5 学生评教 ｜ T6 红线检查
    （T1~T5 可并行，T6 单独执行并直接决定最终标记）
 3. Retriever（每个 T）：查指标仓库/落库结果 → 无则走 SQL 聚合 → 生成 evidence_block。
 4. Analyzer（每个维度 Worker）：得分 = f(指标值, benchmark, confidence_rule)；
    输出 {dimension_score, confidence, evidence_ids, gap_reasons}。
 5. Synthesizer：按模板权重加权 → total_score；
    缺失维度按"不参与加权+单独披露"处理（或按最大熵法置信度加权，需配置）。
 6. Critic 校验：无证据结论？矛盾？样本过小未披露？红线上级别误判？
    → 打回 Synthesizer 重写，最多 2 轮。
 7. 输出报告：维度雷达图、总分（附置信区间与覆盖率）、各结论证据引用列表、
    数据缺口清单、免责声明（发展性参考，非人事裁决）。
```

### 4.3 置信度模型（草案）

```
维度置信度 = 1 - Σ penalty
  penalty 来源：
    - 样本量过小（听课 <3 次、评教 <20 份、班级 <10 人）
    - 数据断档（对应学年无记录）
    - 数据质量分低（ETL 校验空值率/异常值率超阈值）
    - 指标口径存在歧义（口径字典未覆盖）

综合置信度 = 权重 × 维度置信度的加权平均（仅对已覆盖维度）
数据覆盖率   = 已覆盖维度权重和 / 总权重和（红线维度除外）
```

**输出规则**：`覆盖率 < 0.6` 时报告顶部明示"数据覆盖不足，结论仅供参考"；任一关键维度置信度 < 0.5 时该维度结论降级为"趋势性提示"。

### 4.4 质疑机制（Critic 规则示例）

- 结论中出现的数字必须在 `evidence_block` 中有来源（正则/引用校验）。
- "某维度最好/最差"类比较必须有同口径对比证据。
- 单一学期小样本不允许多学期趋势论断。
- 红线项与师德相关措辞使用中性表述，不做人格化评价。

## 5. Agent 编排实现方案

### 5.1 技术路线：LangGraph（首选）与自研状态机（备选）

```
状态节点：parse → clarify? → plan → retrieve → analyze(并行) → synthesize → critic → respond
条件边：  clarify(需要反问?) —— yes → 询问用户后回 plan
          critic(校验不通过?) —— yes → synthesize(重写, ≤2轮)
工具：    tool_sql_query(只读, 白名单表) / tool_vector_search(文档) / tool_template_load / tool_cycle_load
```

- Planner 产出的是**结构化任务 DAG（JSON）**，不是自由文本计划，便于并行调度与审计。
- 每个 Analyzer Worker 独立上下文，只带"该维度的证据块 + 该维度规则"，减少串扰与 token 消耗。
- Critic 用独立 Prompt + 独立（或双）模型。

### 5.2 稳定内存与一致性

- **会话记忆**：`session_memory` 表，存对话要点（对象、范围、已给结论摘要），追问时复用。
- **结论缓存**：`evaluation_result` 按 (teacher, cycle, template) 唯一化，同题同答取缓存；数据更新后失效重建。
- **温度策略**：评估类最终生成温度 = 0~0.2；创意类模板生成可用 0.7。

## 6. API 草案（REST，v1）

### 6.1 评估 API

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/chat` | 对话式评估主入口（流式 SSE 可选） |
| POST | `/api/v1/evaluations` | 发起批量评估任务 |
| GET  | `/api/v1/evaluations/{result_id}` | 获取评估结果（含维度得分与证据） |
| GET  | `/api/v1/teachers/{teacher_id}/reports` | 某教师历次评估报告列表 |
| GET  | `/api/v1/teachers/{teacher_id}/reports/{result_id}` | 单份报告快照 |
| GET  | `/api/v1/teachers/{teacher_id}/trends` | 多周期趋势（雷达图数据） |
| POST | `/api/v1/evaluations/{result_id}/export` | 导出 PDF/Word |

### 6.2 配置与治理 API

| 方法 | 路径 | 说明 |
|---|---|---|
| CRUD | `/api/v1/templates` | 评估模板维护（草稿→生效流程） |
| CRUD | `/api/v1/templates/{id}/rules` | 维度/指标/权重配置 |
| GET  | `/api/v1/glossary` | 口径字典 |
| CRUD | `/api/v1/model-providers` | 模型供应商配置（密钥加密存储） |
| GET  | `/api/v1/data-sources` | 数据源接入状态 |
| GET  | `/api/v1/audit-logs` | 审计查询（管理员） |

### 6.3 数据权限规则（实现要点）

- 中间件做三层校验：登录(JWT) → 角色 → 数据范围（如教师本人只能访问 `teacher_id 属于我` 的资源，教研员可按教研组范围，教务可按全校）。
- 报告导出 API 记录审计；导出含红线标记的报告需二次授权。
- 所有对业务库的查询一律走只读账号 + 视图白名单。

## 8. 关键设计决策清单（供评审）

| # | 决策 | 理由 |
|---|---|---|
| D1 | 指标计算走 SQL/聚合直算，不走 LLM | 数值精确性不能交给模型；LLM 只做解读与综合 |
| D2 | 评估结论必须挂证据块 | 防幻觉的硬约束 |
| D3 | 权重/口径业务方配置 + 版本化 | 评估的"合法性"来自业务方而非算法 |
| D4 | 红线项一票否决、不加权 | 师德问题不适合用分数稀释 |
| D5 | 效果类指标用基线/增值口径 | 避免优质班级教师被误伤 |
| D6 | 模型层统一网关 + 双模型校验（高利害题） | 供应商解耦 + 容错 + 交叉验证 |
| D7 | 教师主数据用内部 ID 去标识化 | 面向用户分析库最小化暴露实名信息 |
| D8 | 对话式与批量式共用同一评估管线 | 保持一致性与可维护性 |

## 9. 迭代与交付节奏（P0 细化）

1. **第 1~2 周**：需求确认单签字、数据盘点（含 1~2 个系统样例）、指标框架 v1 评审。
2. **第 3~4 周**：DDL 基线、ETL 接入成绩+评教、指标计算管线跑通、前端壳搭建 + 登录。
3. **第 5~8 周**：单模型对话问答（有反问、有证据引用）、批量评估任务、20 例样例报告与业务验收。
4. 之后进入大纲 P2（多模型路由、Critic、Golden Set 回归）。
